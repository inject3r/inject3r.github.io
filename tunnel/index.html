01/overview

What tunnel is, what it ships, and how it is built.

What tunnel is / overview

tunnel is written in C++20 for Linux and is designed around proxy pools rather than a single hard-coded upstream. It can expose local proxy endpoints, run applications through a proxy-aware command mode, or enforce system-wide interception through nftables. The central design principle is simple: connectivity failures should switch upstreams safely instead of silently leaving the host without a recovery path.

Upstream: SOCKS4 / SOCKS4aUpstream: SOCKS5 / SOCKS5hLocal HTTP CONNECTLocal SOCKS5Local HTTP CONNECT listenernftables Global Mode

Features / features

Everything included in tunnel 1.1.0.

F.01
Proxy pools

Load multiple upstream proxies from a plain-text list and use that pool within the selected running mode.

F.02
Sticky selection

Pick the best reachable proxy once, then keep it active until a real upstream connection failure occurs.

F.03
Opt-in auto switch

Periodic fastest-proxy re-selection is disabled by default and only enabled with --auto-switch SEC.

F.04
Bounded failover

The default upstream connection and probe timeout is 8 seconds before failover can move to another healthy proxy.

F.05
Tor SOCKS5h integration

Use a local Tor SOCKS listener directly, with optional Tor Browser port selection and per-run SOCKS stream isolation credentials.

F.06
Tor-safe Global UDP handling

When the selected upstream is Tor, transparent UDP interception is disabled instead of assuming SOCKS5 UDP support.

F.07
Local HTTP CONNECT

Expose a local Local HTTP CONNECT listener for software that expects an HTTP proxy endpoint.

F.07
Kernel Global Mode

Intercept local traffic with nftables and redirect it through tunnel's local data plane.

F.08
Preflight before firewall

Real TCP + proxy CONNECT preflight succeeds before a fail-closed firewall transaction is committed.

F.09
DNS-safe resolution

Proxy hostnames are resolved before fail-closed rules are installed and resolved endpoints are cached for upstream connects.

F.10
Network-change recovery

Interface, route, and Wi-Fi changes trigger one-shot upstream revalidation without silently enabling periodic proxy rotation.

F.11
Independent firewall guardian

A guardian can remove orphaned firewall state if the main daemon crashes or is force-killed.

F.12
Emergency recovery

--emergency-disable-global provides a hard cleanup path when normal shutdown is unavailable.

Architecture / architecture

The release separates CLI parsing, proxy handling, data-plane servers, mode orchestration, configuration, and Global Mode logic into dedicated C++ headers with a small entry point.

L.01
Proxy layer

Parses supported upstream URLs, resolves endpoints, handles configured credentials, and performs HTTP or SOCKS handshakes.

L.02
Pool layer

Selects healthy upstreams, tracks the active proxy, performs latency checks, and implements sticky failover or opt-in rotation.

L.03
Server layer

Provides the local SOCKS5 server and the Local HTTP CONNECT listener used by Global Mode, passing destination streams to the upstream pool.

L.04
Global layer

Coordinates transparent listeners, preflight checks, nftables rules, endpoint caching, network recovery, state, and guardian cleanup.

Global startup contract: listeners → upstream TCP + proxy CONNECT preflight → nft -c validation → firewall commit → READY/ACTIVE state.
02/usage

Build, configure, and run tunnel.

Quick start / quick start

Build

bash — build
$ ./build.sh
$ ./build/tunnel --version
$ ./tests/cli-smoke.sh ./build/tunnel

Use a proxy list

bash — run
# global mode with explicit list
$ sudo ./build/tunnel --enable-global --file /path/to/proxies.txt

For normal global operation, the proxy list is intentionally explicit. You can later configure a persistent default path so --file is no longer necessary.

Proxy files / proxy files

tunnel never falls back to an implicit filename in the current directory. When --file is omitted, the application uses only the persisted path configured with --set-proxy-file.

bash — persistent proxy list
# user-level persistent default
$ ./tunnel --set-proxy-file /home/me/proxies.txt
$ ./tunnel --show-proxy-file

# system-wide default
$ sudo ./tunnel --set-proxy-file /etc/tunnel/proxies.txt
$ sudo ./tunnel --show-proxy-file
$ sudo ./tunnel --enable-global

# one-run override
$ sudo ./tunnel --enable-global --file /tmp/other-proxies.txt

# remove the persistent default
$ sudo ./tunnel --clear-proxy-file
Input format: one supported proxy URL per line. Supported upstream schemes are http://, socks4://, socks4a://, socks5://, and socks5h://. Credentials can be included in supported proxy URLs. https:// upstream proxies are not supported because the current backend has no TLS transport for the proxy connection itself.

Tor integration / tor

--tor selects a local Tor SOCKS listener as the upstream. Tunnel uses socks5h:// so hostname resolution can stay inside Tor unless --local-dns is explicitly requested.

bash — Tor examples
# System Tor (normally 127.0.0.1:9050)
$ ./tunnel --tor curl https://ifconfig.me

# Tor Browser (normally 127.0.0.1:9150)
$ ./tunnel --tor-browser curl https://ifconfig.me

# Custom Tor listener
$ ./tunnel --tor-host 127.0.0.1 --tor-port 9050 curl https://example.com

# Fresh SOCKS credentials for Tor stream isolation
$ ./tunnel --tor --tor-isolate curl https://example.com

# Test Tor through the normal upstream preflight
$ ./tunnel --tor-check
Tor UDP limitation: the local Tor SOCKS interface is TCP-oriented. Tunnel therefore disables transparent UDP interception in Global Mode when --tor is selected. TCP interception and the local DNS fallback remain available.
No proxy list required: --tor, --tor-browser, and --proxy URL create a direct upstream selection and bypass the persistent proxy-file requirement.

Server mode / server mode

Server mode keeps the local application-facing side simple: clients connect to tunnel, and tunnel chooses an upstream from the configured pool.

SOCKS5

bash — local server
$ ./tunnel --server --file /path/to/proxies.txt

# custom bind / port
$ ./tunnel --server --host 127.0.0.1 --port 9050 --file /path/to/proxies.txt

Fixed upstream

bash — single proxy
$ ./tunnel --server \
    --proxy socks5://user:password@proxy.example:1080 \
    --port 9050

Non-loopback SOCKS5 binds require local authentication. Use --auth-user and --auth-pass when exposing a listener beyond localhost.

Fixed upstream: --proxy is a standalone upstream selector. It does not require --file PATH or a previously configured proxy-list default.

Verification

bash — verify upstream
$ ./tunnel --server --verify --file /path/to/proxies.txt

Command mode / command mode

Command mode starts the local proxy path, exports standard proxy environment variables for the child process, and handles Firefox with a temporary isolated profile unless that behavior is explicitly disabled.

bash — command mode
# generic command
$ ./tunnel --proxy socks5h://user:password@proxy.example:1080 curl https://ifconfig.me

# firefox
$ ./tunnel firefox --file /path/to/proxies.txt

# disable firefox temporary profile
$ ./tunnel --no-firefox-special firefox --file /path/to/proxies.txt
Local proxy: command mode uses a temporary local SOCKS5 server as the child process's proxy endpoint. The process environment can include ALL_PROXY / all_proxy and the project also exposes a TELEGRAM_PROXY value for compatible workflows.
03/global-mode

System-wide interception, failover, and recovery.

Enabling Global Mode / global mode

Global Mode uses local redirect listeners plus nftables to intercept normal host traffic. It is intended for Linux systems where you need traffic to follow the proxy pool without manually configuring each application.

Startup sequence

pipeline — fail-closed
  [1]  resolve proxy hostnames → cache IPv4 / IPv6 endpoints
  [2]  start local interception listeners
  [3]  real upstream TCP + proxy CONNECT preflight
  [4]  if preflight fails → stop listeners, leave firewall untouched
  [5]  validate generated nftables rules with nft -c
  [6]  commit the firewall transaction
  [7]  publish READY / ACTIVE state

Enable

bash — global mode
$ sudo ./tunnel --enable-global

Periodic fastest-proxy switching

bash — rotation (opt-in)
# disabled by default
$ sudo ./tunnel --enable-global --auto-switch 15

# compatibility alias
$ sudo ./tunnel --enable-global --ping-interval 15

Without those flags, tunnel does not keep replacing the active proxy simply because another proxy later reports a lower ping.

Optional desktop proxy integration

bash — system proxy
$ sudo ./tunnel --enable-global --system-proxy

System proxy integration is opt-in. Global Mode does not modify GNOME/KDE, /etc/environment, APT proxy settings, or the systemd manager environment unless explicitly requested.

Recovery & safety / recovery

Global Mode is not supposed to leave a machine in a permanent fail-closed state. Recovery is deliberately independent from ordinary daemon success paths.

R.01
Firewall guardian

An independent watchdog can remove orphaned tunnel nftables state after a crash or forced termination.

R.02
Network-change revalidation

Kernel network events can trigger a one-shot upstream revalidation after a Wi-Fi, interface, or route change.

R.03
Standalone disable

--disable-global performs network-independent firewall cleanup before and after daemon termination.

R.04
Emergency cleanup

--emergency-disable-global is the hard recovery path when normal state is incomplete or a daemon is wedged.

bash — recovery
# normal recovery
$ sudo ./tunnel --disable-global

# hard recovery
$ sudo ./tunnel --emergency-disable-global

# inspect current state
$ ./tunnel --global-status
Important: Global Mode requires root-level networking capabilities. Keep the recovery commands available before enabling a kernel-enforced configuration on a remote or fragile host.

Proxy selection / selection

tunnel separates initial quality selection from runtime failover. This prevents constant proxy churn on noisy networks.

behaviordefaultwhat happens
Initial selectionEnabledProbe reachable upstreams with real TCP + proxy CONNECT and choose the lowest-latency successful proxy.
Sticky runtimeEnabledKeep the chosen upstream until a connection attempt actually fails.
Connection failoverEnabledMove to another healthy proxy after a bounded upstream timeout or failure.
Periodic re-selectionDisabledOnly runs when --auto-switch SEC or --ping-interval SEC is supplied.
Health timeout8 secondsUsed for upstream ping/preflight and normal connection timeout defaults.
bash — latency probe
# inspect proxy latency without enabling Global Mode
$ ./tunnel --check-ping --file /path/to/proxies.txt

DNS & networking / dns

N.01
Endpoint cache

Proxy hostnames are resolved before the firewall closes normal egress and each proxy stores its resolved IPv4/IPv6 endpoints.

N.02
SOCKS5 correctness

SOCKS5 upstream connections reuse cached proxy endpoints instead of forcing a second DNS dependency after the firewall is active.

N.03
DNS fallback

UDP/53 is redirected to a dedicated local DNS path and forwarded over TCP through the proxy pool.

N.04
Marked egress

Interceptor and upstream sockets use SO_MARK so nftables can distinguish proxy egress and avoid recursive interception.

N.05
Protocol exceptions

IPv4 ICMP, IPv6 ICMPv6, and local/link-local traffic have explicit exceptions in the generated rules.

N.06
UDP limitation

Generic UDP interception requires a SOCKS5/SOCKS5h upstream because the data plane uses SOCKS5 UDP ASSOCIATE.

Security / security

Operational safety is part of the design.

S.01
Dedicated firewall namespace

Global Mode uses dedicated nftables table and rule names instead of flushing unrelated host rules.

S.02
Pre-commit validation

Generated firewall rules are syntax-checked with nft -c -f before application.

S.03
Credential masking

Proxy credentials are masked in normal diagnostic output.

S.04
Capability scoping

The systemd unit is designed to bound required kernel networking capabilities.

S.05
Private proxy files

Credential-bearing proxy files should be owned by the correct user and stored with restrictive permissions such as 0600.

S.06
Standalone recovery

Global shutdown is intentionally available as a separate, recovery-focused command path.

Scope & limitations / limits

Requirements and limitations of 1.1.0.

  • Linux is the primary target; Global Mode depends on root-level networking capabilities, nftables, and kernel networking features.
  • The current data plane uses blocking socket operations and per-connection threads.
  • The Global backend currently uses REDIRECT, with limitations around UDP and original-destination handling. TPROXY is planned as a future backend and is not implemented in 1.1.0.
  • https:// upstream proxy URLs are not supported because the current proxy-to-proxy transport does not implement TLS.
  • Generic UDP interception requires an available SOCKS5/SOCKS5h upstream.
05/faq

Frequently asked questions

Does tunnel constantly replace the proxy with the lowest ping?
No. The default behavior is sticky selection: choose the best reachable proxy once, keep it, and fail over only when the active upstream fails. Periodic replacement requires --auto-switch SEC or --ping-interval SEC.
Do I have to pass --file every time?
No. Run --set-proxy-file PATH once and tunnel can use the persisted proxy-list path whenever --file is omitted.
What happens if the Wi-Fi connection changes while Global Mode is active?
Kernel network events trigger a one-shot upstream revalidation. The recovery path is separate from periodic fastest-proxy rotation, so a Wi-Fi change does not silently enable constant proxy switching.
What if the Global daemon crashes?
The independent firewall guardian is designed to remove orphaned tunnel nftables state. The standalone --emergency-disable-global path provides an additional hard cleanup mechanism.
Does Global Mode change desktop proxy settings automatically?
No. System proxy integration is opt-in through --system-proxy.
Is tunnel a VPN?
No. It is a proxy-based Linux networking tool. Global Mode uses nftables and local interception listeners to redirect traffic through upstream proxies.
